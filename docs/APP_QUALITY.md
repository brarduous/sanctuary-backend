# Application quality and reader evidence

## Production jobs and reports

`npm run cron-app-quality` runs hourly at minute 15 (UTC). It reads the actual anonymous public APIs and checks devotional continuity, seven-day trivia availability, news freshness, notification-provider outcomes, server timings, partial token totals, reader responses and dated privacy release evidence. Failures and warnings remain visible. A nonzero process exit marks `needs_attention`; reports remain stored for diagnosis. This job never sends notifications or publishes content.

`npm run cron-content-quality` runs Mondays at 06:30 UTC, after the devotional improvement job at 06:00 UTC. Its lookback is fourteen days to obtain at most three recent samples per content type, rather than pretending every type has a daily supply. The devotional improvement job reviews the previous Monday–Sunday UTC week. Local wall-clock times change with daylight saving.

The broader content audit uses `gpt-6-astra` for general/personal devotionals, prayers, guidance, sermons, studies, news, briefs and trivia. At most three recent samples per type are graded; nine 6,000-completion-token assessments bound the audit. The automated acceptance floor is an average editorial score of 85/100, with accuracy at least 85, helpfulness/audience at least 75, freshness at least 60, and no serious factual or safety concern. This is an editorial estimate, not an 85% probability or representative audience research. The existing independently verified trivia evidence threshold remains 95; a broad style score cannot override it.

There is no human approval inbox for these findings. Set `CONTENT_QUALITY_AUTOREPAIR_ENABLED=true` on the weekly audit. Failing samples or unavailable assessments enter private `content_quality_replacements`. `npm run cron-content-replacements` processes three jobs every thirty minutes. Each attempt uses a fresh Sol candidate and a separate Astra assessment; news and briefs also require an independent source/Scripture check and their existing publication constraints. Attempts are recorded before paid calls, use fifteen-minute leases, and back off ten minutes, one hour, then twenty-four hours after every third attempt. Failed candidates are not published. Original snapshots, candidate versions and assessments remain in service-only history and private histories cascade when the owning account is deleted.

Source edits made during generation make the candidate obsolete rather than overwriting newer work. Uploaded/author-provided sermon manuscripts are retained automatically without creating an approval task. Explicit prior rejection or archival is honored. A serious public news/brief concern withholds that copy while replacement runs. Generic reconciliation cannot republish a story reserved for automatic replacement. Trivia revisions remain immutable: a failed revision is retired and delivery substitutes another complete, independently approved set; it never patches answers or lowers its evidence gate. Private content stays scoped to its original recipient, and does not tune another reader's prompt. The separately guarded devotional prompt/model improvement loop continues to test promotions.
Administrators can read `/admin/quality` and the web `/quality` page. The API uses authenticated server-side role checks. Operational, editorial and release evidence are separate. Unknowns have no score, there is no overall average, and a good content score never offsets a failed privacy or availability check.

## Reader feedback

The web devotional detail page optionally asks whether the reading helped, whether its practice feels feasible, and which predefined issues apply. Responses can be changed or removed. There is no free-text field. The API verifies ownership of private completed content or availability of released public content. It derives identity from the session, limits requests, and disables caching. Raw feedback has no anonymous or authenticated database access; service-only API access enforces ownership.

Reports distinguish response count from unique readers, mark fewer than five respondents as insufficient sample, and disclose optional-response bias. Perceived feasibility does not prove the reader performed a practice or experienced spiritual growth. Mobile feedback UI is not part of this web release.

## Privacy boundaries and verification

The release includes authenticated route ownership, congregation membership checks and direct database RLS boundaries for private devotional, prayer, guidance, feedback, activity, sermon, series and profile tables. Restrictive policies prevent legacy permissive policies from granting foreign inserts or owner reassignment. Existing study-parent sharing determines lesson visibility; only the parent author may modify lessons. Raw diagnostic logs and prompt evaluations are service-only. Profile display/preferences remain editable while roles, subscription entitlements, billing identifiers and usage controls are server-managed. Existing paid profiles retain entitlements during legitimate client upserts.

`QA_CONFIRM_PRODUCTION=account-isolation node scripts/verifyAccountIsolationProduction.js` creates two disposable confirmed-email accounts, reads only their synthetic private records, verifies both direct database and public HTTP boundaries, then removes its fixtures. It does not send email, publish content or invoke payment. A dated release report records checks and cleanup, not credentials. Two-church membership combinations additionally use isolated HTTP integration tests. This is scoped verification, not a security certification.

Migrations 1800, 1900, 2000, 20261102100000 and 20261102110000 are repeatable. Apply through the normal production migration process before enabling the routes/jobs. Rollback 1800 requires disabling feedback and quality jobs and exporting history first. Rollback 1900 deliberately fails closed: it removes new permissive owner access but retains RLS, restrictive ownership boundaries, profile guards and diagnostic restrictions. It must not restore known private-data exposure. Migration 2000 restricts privileged allowlists and subscription writes to the server, retaining only own-email whitelist and own-account subscription reads for existing clients. Its rollback also fails closed.

## Limits and remaining release work

Real-device VoiceOver/TalkBack, large text, offline/recovery journeys, crash-free sessions and sandbox subscription purchase/restore/cancellation/cross-device entitlement checks require observed device evidence. They are explicitly unmeasured here. Provider acceptance is not proof of notification delivery. Mixed server-operation timings are not screen load latency or user error rates. Token telemetry is incomplete, so no dollar cost is invented.

An initial measurement found a short trivia generation runway and source-attribution concerns in a small news sample. Content findings now trigger automatic replacement. Generation capacity and failed measurements remain operational diagnostics, without requiring the owner to approve a draft. Actual reader outcomes and before/after cohorts require sustained usage evidence; model grades alone cannot establish improvement.

## Engagement-based trivia delivery

Enable `recycle_unplayed_sets` in `discovery_runtime_settings`. `discovery_delivery_days` freezes a coherent three-question set for each displayed date while retaining the original source date and question IDs. When only signed-in admins, internal rollout/test accounts, or QA accounts have answered, the same set carries forward. A normal account's actual answer (right or wrong), or an eligible anonymous `answer_committed` event, permits the next displayed day to use the oldest unused approved set. Reveals, timeouts and page views do not consume it. The current day's selection stays fixed after engagement. Withdrawals can replace the whole set with another approved set, with the previous mapping recorded; questions are never mixed across separately reviewed sets.

Existing canonical completion rows and unique per-account/question credit are not rewritten. The API presents existing results against the current delivery date while preserving original completion/local dates. The web also recognizes source dates in saved guest progress. Replaying a carried set cannot create a second completion or a new win from yesterday's play. Original publication archives remain intact and retain their access rules. The same backend serves the current native app; no native binary is required for the delivery change.

Admin/test exclusions depend on authenticated identity. An operator playing anonymously cannot be distinguished from another anonymous visitor, and anonymous answer telemetry is an observed client event rather than proof of a distinct human. Historic anonymous metrics default to ineligible instead of being retroactively called audience participation. No user/device identifier is added to aggregate metric storage.
